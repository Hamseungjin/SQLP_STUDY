# API 응답 시간만으로 DB 성능 개선을 판단하면 안 되는 이유

개발자들이 포트폴리오나 기술 블로그에서 “DB 성능 개선을 했다”, “인덱스를 걸어 쿼리를 튜닝했다”고 말하는 경우가 많다.

하지만 실제 내용을 보면 DB 내부에서 무슨 일이 일어났는지 분석하지 않고, 단순히 API 응답 시간이 줄어든 것만 보고 성능 개선이라고 판단하는 경우가 있다.

예를 들면 다음과 같은 방식이다.

```text
인덱스 적용 전: /users/search API 응답 1200ms
인덱스 적용 후: /users/search API 응답 300ms

→ 인덱스를 적용했더니 성능이 개선되었다.
````

물론 API 응답 시간이 줄어든 것은 의미 있는 결과일 수 있다.
하지만 이것만으로는 “DB 쿼리가 왜 빨라졌는지”를 설명하기 어렵다.

---

## API 응답 시간은 DB 쿼리 시간만 의미하지 않는다

API 응답 시간에는 DB 쿼리 실행 시간뿐만 아니라 여러 과정이 포함된다.

```text
클라이언트 요청
→ 네트워크
→ WAS
→ 애플리케이션 로직
→ DB 커넥션 획득
→ SQL 실행
→ 결과 매핑
→ JSON 변환
→ 응답 반환
```

즉, `/users/search` API의 응답 시간이 줄었다고 해서 반드시 DB 쿼리 자체가 빨라졌다고 단정할 수는 없다.

응답 시간이 줄어든 이유는 다음과 같은 다른 요인일 수도 있다.

```text
캐시가 적용되었을 수 있다.
JVM이 워밍업되었을 수 있다.
DB 버퍼 풀에 데이터가 올라와 있었을 수 있다.
네트워크 상태가 달랐을 수 있다.
동시 요청 수가 달랐을 수 있다.
커넥션 풀 상태가 달랐을 수 있다.
테스트 데이터가 달랐을 수 있다.
```

따라서 API의 elapsed time만 비교하고 “쿼리 튜닝 성공”이라고 말하는 것은 분석의 깊이가 부족할 수 있다.

---

## DB 튜닝에서 확인해야 할 것들

DB 성능 개선을 제대로 설명하려면 단순히 응답 시간이 줄었다는 결과뿐만 아니라, DB 내부에서 어떤 변화가 있었는지를 함께 보여줘야 한다.

대표적으로 다음 항목들을 확인할 수 있다.

```text
실행 계획 확인
인덱스 사용 여부 확인
읽은 row 수 확인
스캔 방식 확인
조인 방식 분석
정렬/그룹화 비용 확인
불필요한 컬럼 제거
페이지네이션 방식 개선
통계 정보 확인
데이터 분포 확인
커버링 인덱스 적용 여부 확인
```

핵심은 “빨라졌다”가 아니라, **왜 빨라졌는지 설명할 수 있어야 한다는 것**이다.

---

## 실행 계획을 통한 분석 예시

예를 들어 기존 쿼리가 다음과 같은 문제가 있었다고 하자.

```text
WHERE 조건에 맞는 인덱스가 없어 full table scan이 발생했다.
```

MySQL 기준으로 `EXPLAIN`을 확인했을 때 다음과 같은 결과가 나왔다고 볼 수 있다.

```text
type = ALL
rows = 1,000,000
```

여기서 `type = ALL`은 테이블 전체를 스캔하고 있다는 의미다.
`rows = 1,000,000`은 DB가 약 100만 건 정도의 데이터를 읽을 것으로 예상했다는 의미다.

즉, 원하는 데이터는 일부인데도 인덱스를 제대로 활용하지 못해서 많은 데이터를 읽고 있었던 것이다.

---

## 복합 인덱스 적용 후 변화

이 문제를 해결하기 위해 다음과 같은 복합 인덱스를 추가했다고 하자.

```sql
CREATE INDEX idx_user_created_at
ON orders(user_id, created_at);
```

이 인덱스는 다음과 같은 쿼리에 도움이 될 수 있다.

```sql
SELECT id, user_id, created_at
FROM orders
WHERE user_id = ?
ORDER BY created_at DESC;
```

복합 인덱스를 추가한 뒤에는 `WHERE user_id = ?` 조건과 `ORDER BY created_at DESC` 정렬이 인덱스를 활용할 수 있게 된다.

그 결과 실행 계획이 다음처럼 바뀔 수 있다.

```text
type = range 또는 ref
rows = 120
```

기존에는 100만 건을 읽을 것으로 예상되었지만, 인덱스 적용 후에는 약 120건만 읽는 방식으로 바뀐 것이다.

---

## 커버링 인덱스를 통한 추가 개선

또한 `SELECT`하는 컬럼을 인덱스에 포함된 컬럼으로 제한하면 커버링 인덱스가 적용될 수 있다.

커버링 인덱스란 쿼리에 필요한 데이터를 실제 테이블까지 가지 않고 인덱스만으로 처리할 수 있는 경우를 말한다.

예를 들어 인덱스가 다음과 같이 구성되어 있다고 하자.

```sql
CREATE INDEX idx_user_created_at
ON orders(user_id, created_at, id);
```

그리고 쿼리가 다음과 같다면:

```sql
SELECT id, user_id, created_at
FROM orders
WHERE user_id = ?
ORDER BY created_at DESC;
```

이 쿼리에 필요한 컬럼인 `id`, `user_id`, `created_at`이 모두 인덱스에 포함되어 있다.

이 경우 DB는 실제 테이블에 접근하지 않고 인덱스만으로 결과를 만들 수 있다.
그만큼 디스크 I/O나 테이블 접근 비용이 줄어들 수 있다.

---

## 개선 결과를 설명하는 좋은 방식

단순히 다음처럼 말하는 것은 부족하다.

```text
인덱스를 추가했더니 API 응답 시간이 1200ms에서 300ms로 줄었다.
```

조금 더 좋은 설명은 다음과 같다.

```text
기존 쿼리는 WHERE 조건에 맞는 인덱스가 없어 full table scan이 발생했다.

EXPLAIN 결과 type이 ALL이었고, rows 예상치는 약 100만 건이었다.

(user_id, created_at) 복합 인덱스를 추가한 뒤,
WHERE user_id = ? 조건과 ORDER BY created_at DESC가 인덱스를 활용하게 되었다.

그 결과 EXPLAIN 결과에서 type이 range/ref로 바뀌었고,
rows 예상치가 100만 건에서 약 120건으로 줄었다.

또한 SELECT 컬럼을 인덱스에 포함된 컬럼으로 제한하여 커버링 인덱스가 적용되었고,
실제 테이블 접근이 줄어들었다.

최종적으로 DB 쿼리 실행 시간은 850ms에서 40ms로 감소했고,
API 응답 시간도 함께 개선되었다.
```

## 결론

DB 성능 개선을 이야기할 때 API 응답 시간이 줄어든 결과만 보여주는 것은 부족하다.

API 응답 시간에는 네트워크, WAS, 애플리케이션 로직, 커넥션 풀, 캐시, JSON 변환 등 여러 요소가 포함되기 때문이다.

따라서 DB 튜닝을 했다고 말하려면 다음과 같은 근거를 함께 제시해야 한다.

```text
실행 계획이 어떻게 바뀌었는가?
인덱스를 실제로 사용하고 있는가?
full table scan이 index scan으로 바뀌었는가?
읽는 row 수가 얼마나 줄었는가?
정렬이나 그룹화 비용이 줄었는가?
커버링 인덱스가 적용되었는가?
DB 쿼리 실행 시간이 얼마나 줄었는가?
```

결국 중요한 것은 단순히 “빨라졌다”가 아니다.

**무엇이 병목이었고, 어떤 변경으로 인해, DB 내부 동작이 어떻게 바뀌었으며, 그 결과 얼마나 개선되었는지를 설명할 수 있어야 한다.**
