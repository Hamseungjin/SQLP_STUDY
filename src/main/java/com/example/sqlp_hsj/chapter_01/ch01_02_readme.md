# Orders 테이블 인덱스와 선택도 실습

## 1. 테스트 데이터

`BulkOrderDataLoader.java`를 실행하면 `orders` 테이블에 대량의 주문 데이터가 생성된다.

### status 컬럼 값

`status` 컬럼은 다음 5가지 값 중 하나를 가진다.

- `CREATED`
- `PAID`
- `SHIPPED`
- `CANCELLED`
- `REFUNDED`

### 데이터 개수

총 데이터 수는 약 100만 건이다.

---

## 2. 인덱스 확인하기

MySQL에서는 다음 명령어로 특정 테이블에 걸린 인덱스를 확인할 수 있다.

```sql
SHOW INDEX FROM orders;
````

주요 컬럼의 의미는 다음과 같다.

| 컬럼명            | 의미                         |
| -------------- | -------------------------- |
| `Key_name`     | 인덱스 이름                     |
| `Column_name`  | 인덱스에 포함된 컬럼                |
| `Seq_in_index` | 복합 인덱스에서 컬럼 순서             |
| `Non_unique`   | `0`이면 유니크 인덱스, `1`이면 중복 허용 |
| `Cardinality`  | 대략적인 고유값 수 추정치             |
| `Index_type`   | 인덱스 타입. 보통 `BTREE`         |

## 3. 선택도란?

선택도란 조건으로 데이터를 조회했을 때, 전체 데이터 중 얼마나 적은 row만 남는지를 의미한다.

쉽게 말하면 다음과 같다.

> 조건을 걸었을 때 적은 데이터만 남을수록 선택도가 좋다.

예를 들어 100만 건 중 10건만 조회된다면 선택도가 좋다고 볼 수 있다.
반대로 100만 건 중 30만 건이 조회된다면 선택도가 좋다고 보기 어렵다.

일반적으로 고유한 값이 많을수록 선택도가 좋다.

예를 들어 `customer_id`는 고객마다 값이 다양하므로 선택도가 좋은 편이다.
반면 `status`는 값이 5개뿐이므로 단독 조건으로는 선택도가 낮을 수 있다.

---

## 4. 인덱스를 사용해도 항상 빠른 것은 아니다

인덱스는 적은 row를 빠르게 찾을 때 효과적이다.

하지만 다음과 같은 경우에는 인덱스를 사용해도 성능 이점이 크지 않을 수 있다.

* 조건 결과가 너무 많은 경우
* `SELECT *`로 많은 컬럼을 가져오는 경우
* 인덱스 컬럼에 함수를 적용하는 경우
* 조건의 선택도가 낮은 경우

즉, 인덱스가 있다고 무조건 빠른 것이 아니라, 인덱스를 통해 얼마나 적은 row를 읽을 수 있는지가 중요하다.

## 5. 고객별 주문 수 확인

다음 쿼리로 주문 수가 많은 고객을 확인할 수 있다.

```sql
SELECT customer_id, COUNT(*) AS order_count
FROM orders
GROUP BY customer_id
ORDER BY order_count DESC
LIMIT 10;
```

실행 결과 예시는 다음과 같다.

```text
+-------------+-------------+

+-------------+-------------+
|        6789 |          27 |
|       12776 |          26 |
|       10692 |          25 |
|       39157 |          24 |
|       69368 |          24 |
|       17500 |          24 |
|       71235 |          24 |
|       33613 |          24 |
|       12573 |          23 |
|         888 |          23 |
+-------------+-------------+
```

`customer_id = 6789`인 고객은 주문이 27건 있다.

## 6. customer_id 조건 조회

다음 쿼리의 실행 계획을 확인한다.

```sql
EXPLAIN
SELECT *
FROM orders
WHERE customer_id = 6789;
```

실행 결과는 다음과 같다.

```text
+----+-------------+--------+------------+------+----------------------------+----------------------------+---------+-------+------+----------+-------+
| id | select_type | table  | partitions | type | possible_keys              | key                        | key_len | ref   | rows | filtered | Extra |
+----+-------------+--------+------------+------+----------------------------+----------------------------+---------+-------+------+----------+-------+
|  1 | SIMPLE      | orders | NULL       | ref  | idx_orders_customer_status | idx_orders_customer_status | 8       | const |   27 |   100.00 | NULL  |
+----+-------------+--------+------------+------+----------------------------+----------------------------+---------+-------+------+----------+-------+
```

### 해석

```text
WHERE customer_id = 6789
```

조건에서는 복합 인덱스 `idx_orders_customer_status` 중 첫 번째 컬럼인 `customer_id`만 사용된다.

예상 읽기 row 수는 27건이다.

| 조건                   | 사용한 인덱스 부분    | key_len | rows |
| -------------------- | ------------- | ------: | ---: |
| `customer_id = 6789` | `customer_id` |       8 |   27 |

복합 인덱스가 다음과 같이 구성되어 있다고 가정하면,

```text
(customer_id, status)
```

왼쪽부터 순서대로 사용할 수 있기 때문에 `customer_id` 조건만 있어도 인덱스를 사용할 수 있다.

---

## 7. customer_id + status 조건 조회

다음 쿼리의 실행 계획을 확인한다.

```sql
EXPLAIN
SELECT *
FROM orders
WHERE customer_id = 6789
  AND status = 'PAID';
```

실행 결과는 다음과 같다.

```text
+----+-------------+--------+------------+------+----------------------------------------------+----------------------------+---------+-------------+------+----------+-------+
| id | select_type | table  | partitions | type | possible_keys                                | key                        | key_len | ref         | rows | filtered | Extra |
+----+-------------+--------+------------+------+----------------------------------------------+----------------------------+---------+-------------+------+----------+-------+
|  1 | SIMPLE      | orders | NULL       | ref  | idx_orders_customer_status,idx_orders_status | idx_orders_customer_status | 90      | const,const |    4 |   100.00 | NULL  |
+----+-------------+--------+------------+------+----------------------------------------------+----------------------------+---------+-------------+------+----------+-------+
```

### 해석

```text
WHERE customer_id = 6789
AND status = 'PAID'
```

조건에서는 복합 인덱스 `idx_orders_customer_status`의 두 컬럼을 모두 사용한다.

예상 읽기 row 수는 4건이다.

| 조건                                       | 사용한 인덱스 부분             | key_len | rows |
| ---------------------------------------- | ---------------------- | ------: | ---: |
| `customer_id = 6789`                     | `customer_id`          |       8 |   27 |
| `customer_id = 6789 AND status = 'PAID'` | `customer_id + status` |      90 |    4 |

`customer_id`만 조건으로 사용할 때는 27건을 읽어야 하지만,
`status = 'PAID'` 조건까지 추가하면 4건만 읽으면 된다.

즉, 조건이 더 구체적이기 때문에 읽어야 하는 데이터 수가 줄어든다.

## 8. 백엔드 API로 이해하기

SQL 인덱스와 선택도는 백엔드 API 설계와도 연결해서 생각할 수 있다.

---

### 좋은 API 조건

```http
GET /customers/6789/orders
```

SQL로 표현하면 다음과 같다.

```sql
SELECT *
FROM orders
WHERE customer_id = 6789;
```

예상 읽기 row 수는 27건이다.

```text
rows = 27
```

특정 고객의 주문만 조회하기 때문에 비교적 좋은 조건이다.

---

### 더 좋은 API 조건

```http
GET /customers/6789/orders?status=PAID
```

SQL로 표현하면 다음과 같다.

```sql
SELECT *
FROM orders
WHERE customer_id = 6789
  AND status = 'PAID';
```

예상 읽기 row 수는 4건이다.

```text
rows = 4
```

특정 고객의 주문 중에서도 `PAID` 상태인 주문만 조회하기 때문에 더 적은 row를 읽는다.

따라서 `customer_id`만 사용하는 API보다 더 효율적이다.

---

### 조심해야 하는 API 조건

```http
GET /orders?status=PAID
```

SQL로 표현하면 다음과 같다.

```sql
SELECT *
FROM orders
WHERE status = 'PAID';
```

예상 읽기 row 수가 매우 많을 수 있다.

```text
rows = 339,992
```

`status`는 값의 종류가 5개뿐이다.

따라서 `PAID` 조건을 걸어도 전체 데이터 중 많은 row가 조회될 수 있다.
데이터가 커질수록 이 API는 느려질 가능성이 높다.

## 9. status 단독 조회를 개선하는 방법

`status`만으로 조회하면 결과가 너무 많을 수 있다.

이런 경우에는 보통 추가 조건을 함께 받도록 API를 설계하는 것이 좋다.

예를 들어 날짜 범위를 함께 받는 방식이다.

```sql
SELECT *
FROM orders
WHERE status = 'PAID'
  AND order_date >= '2024-01-01'
  AND order_date < '2024-02-01';
```

이렇게 하면 `PAID` 상태인 주문 중에서도 특정 기간의 주문만 조회하므로 읽어야 하는 row 수를 줄일 수 있다.

---

## 10. 조회 패턴에 따른 복합 인덱스 고려

날짜 범위를 자주 함께 조회한다면 다음과 같은 복합 인덱스를 고려할 수 있다.

```sql
(status, order_date)
```

또는 날짜 조건이 더 강한 조건이라면 다음 순서도 고려할 수 있다.

```sql
(order_date, status)
```

인덱스 컬럼 순서는 실제 조회 패턴에 따라 결정해야 한다.

예를 들어 다음과 같은 API가 자주 사용된다면,

```http
GET /orders?status=PAID&from=2024-01-01&to=2024-02-01
```

다음 쿼리가 자주 실행될 것이다.

```sql
SELECT *
FROM orders
WHERE status = 'PAID'
  AND order_date >= '2024-01-01'
  AND order_date < '2024-02-01';
```

이 경우에는 `status`, `order_date`를 포함한 복합 인덱스를 검토할 수 있다.

다만 인덱스를 추가하면 다음과 같은 비용이 발생한다.

* INSERT, UPDATE, DELETE 성능 저하
* 추가 저장 공간 사용
* 인덱스 관리 비용 증가

따라서 인덱스는 실제로 자주 호출되는 API와 조회 패턴을 기준으로 결정해야 한다.

---

## 11. 정리

이번 실습에서 확인한 핵심은 다음과 같다.

1. 인덱스는 적은 row를 읽을 때 효과적이다.
2. 선택도가 좋은 조건일수록 인덱스 효율이 좋다.
3. `customer_id`는 고유값이 많아 선택도가 좋은 편이다.
4. `status`는 값 종류가 적어 단독 조건으로는 선택도가 낮을 수 있다.
5. 복합 인덱스 `(customer_id, status)`는 `customer_id` 조건만으로도 사용할 수 있다.
6. `customer_id + status` 조건을 함께 사용하면 더 적은 row를 읽는다.
7. API 설계 시에도 너무 많은 데이터를 조회하는 조건은 피해야 한다.
8. 조회 결과가 많다면 날짜 범위 같은 추가 조건을 받는 것이 좋다.
9. 복합 인덱스는 실제 API 조회 패턴을 기준으로 설계해야 한다.
10. 인덱스 추가는 쓰기 성능과 저장 공간 비용을 함께 고려해야 한다.
